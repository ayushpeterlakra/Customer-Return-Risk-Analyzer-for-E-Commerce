# Machine learning extension

**Everything here is trained and evaluated on synthetic demonstration data.** The results show the pipeline works end to end; they say nothing about real-world fraud.

## Pipeline (`backend/scripts/train.py`)

1. **Labels.** `scripts/seed.py` gives each synthetic customer a hidden behaviour profile (ordinary, frequent but honest returner, new customer, wardrober, vague serial returner, mismatch abuser) and writes it to `backend/data/synthetic_labels.csv`. The last three are labelled 1 ("suspicious pattern"). Labels are not stored in the application database and are never shown as fraud.
2. **Features.** The same `CustomerFeatures` used by the rule engine (`app/ml/features.py` lists the 12 model columns, including `return_ratio` and `vague_reason_share`).
3. **No leakage.** Models never see the rule score or level. One row per customer, so the train/test split is by customer: 80/20, stratified, seed 42. Median imputation (with missing-value indicators) and scaling are fitted inside a scikit-learn `Pipeline`, so only training data shapes them.
4. **Imbalance.** About 20% positives. Both models use `class_weight="balanced"`; we report precision, recall and F1 for the positive class, plus 5-fold cross-validated F1 on the training set.
5. **Threshold.** Chosen to maximise F1 on the training data, never on the test set.
6. **Models.** Logistic Regression (baseline) and a Decision Tree (`max_depth=4`, `min_samples_leaf=5`). The higher test F1 is selected (ties → recall).
7. **Artifacts.** `ml_artifacts/model.joblib` (both pipelines + thresholds) and `ml_artifacts/metrics.json`. Rerun after reseeding.

## Results from the run shipped with this build

Test set: 60 customers, 12 positives. Generated by `python -m scripts.train` on the default seed.

| Model | Accuracy | Precision | Recall | F1 | TN / FP / FN / TP |
| --- | --- | --- | --- | --- | --- |
| Logistic regression (selected) | 0.983 | 1.000 | 0.917 | 0.957 | 48 / 0 / 1 / 11 |
| Decision tree | 0.933 | 0.900 | 0.750 | 0.818 | 47 / 1 / 3 / 9 |
| Rule-based score ≥ 41 (for comparison) | 0.867 | 1.000 | 0.333 | 0.500 | 48 / 0 / 8 / 4 |

How to read this honestly:

- **The test set is tiny** (12 positives). One customer moves recall by about 8 points.
- **The models partly learn the generator.** The tree's top feature is `vague_reason_share`, because the generator writes fewer explanations for suspicious profiles. Real data would not separate this cleanly.
- **The rules are deliberately conservative.** They only flag strong, explainable evidence, so they catch fewer synthetic suspicious profiles (recall 0.33) but flag no ordinary ones.

## Precision versus recall

Recall is the share of suspicious patterns that get flagged; low recall lets abuse go unchecked and costs money. Precision is the share of flagged customers who really show a suspicious pattern; low precision sends honest customers to review, wasting analyst time and risking unfair treatment. A review queue needs both, which is why F1 drives model selection and the threshold.

## Rule score versus ML probability

| | Rule-based score | ML probability |
| --- | --- | --- |
| What it is | Sum of points from published thresholds | Model estimate of resemblance to the synthetic suspicious profiles |
| Explainable by | The factor list | Coefficients / tree splits (in `metrics.json`) |
| Used for | Risk level, review queue | A second opinion on the customer page |

The UI shows both side by side and never merges them. The rule engine is always available; if the model file is missing, `/api/ml/*` answers 503/404 and the rest of the app is unaffected.

## API

- `POST /api/ml/predict` with `{"customer_id": "CUST0046"}` or `{"features": {...}}`, optional `"model": "logistic_regression" | "decision_tree"`.
- `GET /api/ml/metrics` returns `metrics.json`.
